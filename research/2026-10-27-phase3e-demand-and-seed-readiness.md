# Phase 3.0E demand and seed readiness

Date: 2026-10-27 (Africa/Cairo)  
Decision: **production inputs not frozen; Phase 3 execution remains NO-GO**

## Demand pipeline evidence

The offline pipeline can expand supported fixed-number SUMO flows into explicit vehicles, generate
seed-controlled physical realizations, bind route/config/network/additional-file hashes, calculate
a canonical physical fingerprint, and write a non-overwriting split registry. Phase 3.0E adds a
non-overwriting usage-subpool registry that can only be built from a verified five-partition split
registry.

A bounded fixture exercised this complete chain for `training`, `calibration`, `validation`,
`forecast_test`, and `controller_evaluation`. Each generated realization had its own seed and
physical identity. This proves the software path on the fixture; it does not create or approve a
Tahrir publication dataset.

physical fingerprints and the five-pool registry must then be reviewed and frozen. The current
empty demand trust root must not be bypassed.

## Seed identity candidate

`research/2026-10-27-phase3e-seed-allocation-candidate.json` separates all roles:

- policy replicate indices `0..4` map to DQN RNG seeds `11001..11005`;
- forecast replicate indices `0..4` map to candidate RNG seeds `12001..12005`;
- physical demand replicate indices `0..9` map to generation seeds `21001..21010`;
- SUMO execution seeds are profile-specific (`31001..31010`, `31101..31110`,
  `31201..31210`, and `31301..31310`);
- future checkpoint IDs must bind arm, policy index, actual RNG seed and the whole-ensemble
  manifest hash.

The proposed learned-arm rule is `matched_training_seed_v1`: corresponding forecast/no-forecast
policy indices use the same DQN seed, while every eligible checkpoint is crossed with every held-out
physical evaluation demand in its profile. This is deliberately recorded as proposed, not frozen:
`training_seed_pairing_rule` is null and validation with `require_frozen=True` fails.

## Leakage and calibration access

The candidate access policy is:

- `training`: parameter fitting only;
- `calibration`: reward references and other preregistered training-time calibration only;
- `validation`: checkpoint/model selection under the frozen rule;
- `forecast_test`: opened only after forecast model selection;
- `controller_evaluation`: held out until final controller evaluation.

Reward calibration may use deterministic diagnostic controllers on training/calibration demand,
provided their identities and all traces are retained. It must not inspect forecast-test or
controller-evaluation realizations. A controller used to create scale references is not thereby a
research baseline and its outcomes are not performance evidence.

## Gate-0 implementation boundary

`DeepQN/evaluation/gate0.py` validates candidate seed identities, writes a hash-bound usage-subpool
registry, and validates a complete immutable preflight before runtime construction. The validator
does not start SUMO or models and grants no authority. It intentionally rejects the current seed
candidate as unfrozen and rejects null/missing/modified prerequisites. It has not been wired into a
runner because no complete authorized Gate-0 manifest exists and execution was outside Phase 3.0E.
